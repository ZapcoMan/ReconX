# 已知限制与运行验证

本文档只负责一件事：说清 ReconX 的**能力边界、已知限制与验证状态**。能力清单见 [功能与模块说明](功能与模块说明.md)，来源与移植进度见 [技能来源与能力映射](技能来源与能力映射.md)。

下列限制除特别标注外，均为对源码逐文件通读后的静态确认（附代码位置），尚未在真实 Chrome 上复现验证。

## 一、能力边界分级

| 级别 | 含义 | 代码落点 | 触发条件 | 能否关闭 |
|---|---|---|---|---|
| **L1 只读** | 不向目标额外发请求、不修改页面运行时 | `core/router-probe.ts`、`fingerprints`、`header-checks`、`url-classify`、`tech-stack` | 「开始采集」 | 是（不点即可） |
| **L2 主动请求** | 向目标发出额外的真实 HTTP 请求 | `background.runProbes`（19 条敏感路径）、`core/probe-routes.ts`（≤40 条路由）、页面内 `api-extractor.js`（≤80 个 JS + `.map`） | 需点「主动探测」 | 是 |
| **L3 客户端改写** | 修改目标页面前端路由对象、守卫与鉴权 meta | `core/all-in.ts`、`core/detector.ts`（Vue 路径） | ①点「主动探测」时注入；②**入过允许域后每次页面加载自动注入** | **否**，脚本内无任何开关 |

L1 的只读性质经逐函数核验：`router-probe.ts` 全文无 `defineProperty`、无原型/方法替换、无守卫增删、无 `history/location` 写。

## 二、已确认的代码级限制

### 范围与授权

- **移除允许域不会立刻停止接管注入。** 设置页 `remove()` 直接写 `chrome.storage.local` 并 `permissions.remove`，未走 background 的 `REMOVE_HOST`；而常驻脚本重注册只在消息路径与 `onInstalled/onStartup` 触发，也没有 `storage.onChanged` 监听。结果：界面显示"已移除"，该主机在下次增删或重启前仍被注入 `all-in.js`。规避：用设置页「撤销全部主机权限」后重载扩展。
- **主动探测的目标未与标签页绑定。** `RUN_PROBES` 的 `host`/`origin` 来自消息参数，`inScope` 校验的是这个字符串，没有和 `tabId` 的真实 URL 比对，护栏强度依赖调用方自律。
- **`{type: ...}` 消息分支不校验 sender**，仅 `{action: 'reconx*'}` 分支要求 `sender.tab` 存在。
- **`settings.activeProbe` 没有任何消费者。** background 从不读它，界面那个开关是装饰，主动探测完全依赖手动点击。

### 常驻注册与执行时序

- `all-in.js` 以 `document_start + world:MAIN + allFrames` 注册到允许域，注入即无条件安装拦截，`MutationObserver` 永不 disconnect。
- `content.ts` 与注册脚本同为 `document_start`，但 Chrome 不保证两者先后。若 `all-in.js` 先执行，其初始化那次状态上报会丢失，需靠后续拦截事件或 `getAllInStatus` 补发。
- `content.ts` 的 detector 注入锁在 **onload 成功路径不释放**，只靠回传消息解锁；若 `detector.js` 加载成功却没有回传（例如页面早于框架就绪），锁永久卡死，之后该标签页的检测静默失效直到刷新。

### 数据留存与隐私

- **JWT 解码载荷以明文存储**：密钥类命中默认掩码（`sensitive-rules.mask`），但 `jwtDecoded` 会把解码后的 header/payload 原样留下，并随 JSON 导出落盘。
- **响应头原值抵消了 Cookie 掩码**：`header-checks` 的 `cookies[].valueMasked` 是掩码的，但同结构的 `raw` 保留了全部原始头值（含 `Set-Cookie`）。
- **`webRequest` 无范围过滤、无过期**：监听覆盖所有主机，缓存全部站点的响应头直至 service worker 重启。
- **JSON 导出包含完整 URL 与查询参数**，且掩码只在数据源头做、导出不做二次处理。
- 三个注入脚本的回传都使用 `postMessage(..., '*')`，页面内任意脚本可窃听，也可伪造 `data.source` 污染扩展侧缓存（前 3 类结果消息连 `source` 字段都不校验）。

### 未接入界面的核心能力

- 导出的**按等级筛选**（`filterBundle`）、**多目标聚合**（`exportMulti`）、**规则/Dork 库导入**（`parseJson` + `validateImport` + `mergeUser`）核心已实现，但界面无任何调用入口；`exportFullReport` 同样无调用方。
- Dork 库有 25 条通用包 + 34 条教育预设包，结果页只渲染通用包，**教育预设界面不可达**。
- `core/url-utils.ts` 只有一个 `getAllInSiteKey`，全仓零调用，是死代码。
- 上游 CrazyEdusrc 的 `cleanDomain` / `extractSiteTarget`（从 `site:` 反解目标域）与三引擎翻页 URL 尚未移植。
- 主题只有暗色/亮色/极客三档，缺上游的 `system` 跟随系统档。

### 死字段与不匹配

- 报告取 `probes.routes.routeFullUrls`，而 `probe-routes` 只产 `routeProbes` → "共 N 条可访问 URL" 永不渲染；`modifiedRoutes` / `pageAnalysis` / `logs` 同理为死分支。
- `route-urls` 的 base 模式对 React 永不可达：两个调用点都传 `detectedBasePath: null`，且 `collect-extras` 读取了不存在的 `routeBuild.routerBase`。

## 三、判定可靠性风险（容易误信的地方）

1. **"未受保护路由"只看 `meta` 的键名是否存在**，不看值（`requiresAuth: false` 也算已保护）、不看全局 `beforeEach`、不看懒加载子路由 → 极易虚报，也可能漏报。
2. **敏感路径探测的关键词过泛且不校验 Content-Type**：`.env` 只要含 `=`、`package.json` 只要含 `name`、`actuator` 只要含 `health` 即算命中；SPA 的历史回退路由对任意路径返回 200，会把伪造路径判成"存在"。
3. **路由可达性只看状态码与字节数**，`probe-routes` 明确丢弃响应体，200 不等于有内容。
4. **指纹匹配首个命中即返回**，且版本回退到"整条 URL 里抓版本号"；`/ATS/`、`/MT/`、`/mage/`、`XSRF-TOKEN→Laravel` 这类裸词正则会张冠李戴。
5. **响应头风险等级偏高**：HSTS 缺失记 high、CSP 缺失记 medium，非会话类 Cookie 缺 Secure 也一律 medium。
6. **弱信号即会触发 L3**：只要 `window` 里出现 vue/react 字样，`tech-stack` 就判定 SPA 并放行路由探测，进而注入接管脚本——即使该站点根本没有前端路由。

## 四、验证方式

ReconX 是构建型扩展，未引入测试框架。当前可复现的自动化校验有三类：

- **类型与构建**：`npm run typecheck`（`vue-tsc --noEmit`）、`npm run build`（额外产出三个 MAIN world IIFE 脚本并拷入 `dist/`）。
- **纯逻辑断言**（`esbuild` 打包或直接 `node --experimental-strip-types` 运行，不依赖 Chrome）：双源主次判定、存储配额降级、资产测绘矩阵与侦察入口。
- **background 行为回归**：用 mock 的 `chrome` 驱动真实消息处理器，覆盖实时回传串行写入、失败补排、空范围不注册、指令下发、统计字段形状。

上述脚本是开发期验证工具，不在扩展加载路径内，也不随 `npm run build` 执行。

## 五、需 Chrome 实测

以下只能靠加载 `dist/` 验证，目前**均为未验证状态**：

- `document_start` 下 `content.ts` 与常驻注册的 `all-in.js` 谁先执行，首帧状态上报是否丢失。
- 允许域为空、或 host 权限尚未授予时，manifest 里静态声明 `<all_urls>` 的 `content.ts` 到底会不会注入；若不注入，整条 `reconx*` 回传链路在授权前是否完全不通。
- 从设置页移除允许域后，该站点下一次加载是否仍被注入接管脚本（对应第二节的推断）。
- detector 注入锁卡死场景是否可复现。
- `crxjs` 产出的 WAR 路径与 `chrome.runtime.getURL('detector.js')` 是否解析一致。
- 主题切换在长表分页 + 子标签页下的视觉表现；三档主题与 Element Plus 配色联动。
- 授权弹窗、被动采集、主动探测、响应头捕获、导出下载等常规端到端流程。
