# 已知限制与运行验证

本文档只负责一件事：说清 ReconX 的**能力边界、已知限制与验证状态**。能力清单见 [功能与模块说明](功能与模块说明.md)，来源与移植进度见 [技能来源与能力映射](技能来源与能力映射.md)。

下列限制除特别标注外，均为对源码逐文件通读后的静态确认（附代码位置），尚未在真实 Chrome 上复现验证。

## 一、能力边界分级

| 级别 | 含义 | 代码落点 | 触发条件 | 能否关闭 |
|---|---|---|---|---|
| **L1 只读** | 不向目标额外发请求、不修改页面运行时 | `core/router-probe.ts`、`fingerprints`、`header-checks`、`url-classify`、`tech-stack` | 「开始采集」 | 是（不点即可） |
| **L2 主动请求** | 向目标发出额外的真实 HTTP 请求 | `background.runProbes`（19 条敏感路径）、`core/probe-routes.ts`（≤40 条路由）、页面内 `api-extractor.js`（≤80 个 JS + `.map`） | 需点「主动探测」 | 是 |
| **L3 客户端改写** | 修改目标页面前端路由对象、守卫与鉴权 meta | `core/all-in.ts`、`core/detector.ts`（Vue 路径） | ①点「主动探测」时注入；②设置页开启「启用主动探测」后，允许域内每次页面加载自动注入 | 粗粒度可关：总开关关闭时不注册且撤销已有注册；脚本内部无细粒度开关 |

L1 的只读性质经逐函数核验：`router-probe.ts` 全文无 `defineProperty`、无原型/方法替换、无守卫增删、无 `history/location` 写。

## 二、已确认的代码级限制

### 范围与授权

- **常驻接管是设计特性，不是缺陷。** 主机进入允许域、且设置页「启用主动探测」为开时，`all-in.js` 会以 `document_start` 注册进去，此后该站每次加载都自动生效，不需要再点「主动探测」——这是接管能力生效的前提。要停止：关掉总开关（会立即撤销已有注册），或移除该允许域（同样会重算注册）。
- **主动探测的目标未与标签页绑定。** `RUN_PROBES` 的 `host`/`origin` 来自消息参数，`inScope` 校验的是这个字符串，没有和 `tabId` 的真实 URL 比对，护栏强度依赖调用方自律。
- **`{type: ...}` 消息分支不校验 sender**，仅 `{action: 'reconx*'}` 分支要求 `sender.tab` 存在。

### 常驻注册与执行时序

- `all-in.js` 以 `document_start + world:MAIN + allFrames` 注册到允许域，注入即无条件安装拦截，`MutationObserver` 永不 disconnect。
- `content.ts` 与注册脚本同为 `document_start`，但 Chrome 不保证两者先后。若 `all-in.js` 先执行，其初始化那次状态上报会丢失，需靠后续拦截事件或 `getAllInStatus` 补发。
- `content.ts` 的 detector 注入锁在 **onload 成功路径不释放**，只靠回传消息解锁；若 `detector.js` 加载成功却没有回传（例如页面早于框架就绪），锁永久卡死，之后该标签页的检测静默失效直到刷新。

### 数据留存与隐私

- **所有命中一律原文留存，不做掩码**：`sensitive-rules.FindingSample.value` 是命中原文，`header-checks.cookies[].value` 与同结构的 `raw` 保留全部原始头值（含 `Set-Cookie`），`jwtDecoded` 还会把解码后的 header/payload 一并留下。它们都会随 JSON/MD/SRC/HTML/TXT 任一导出落盘——导出文件等同于含真实凭据的取证材料，分享前自行处置。
- **历史结果同样按原文留在本机**：最多 20 份完整结果（`bundle:<id>` 逐条一键），含上述全部原值。要彻底清除，用设置页「采集历史」的逐条删除或清空全部；仅删掉 `lastBundle` 不足以清干净。
- **未申请 `unlimitedStorage`**：配额约 10MB，历史与全量结果共享它。写历史失败时逐条丢最旧重试，最终失败只放弃该条历史，本次采集的 `lastBundle` 不受影响。
- **`webRequest` 无范围过滤、无过期**：监听覆盖所有主机，缓存全部站点的响应头直至 service worker 重启。
- 三个注入脚本的回传都使用 `postMessage(..., '*')`，页面内任意脚本可窃听，也可伪造 `data.source` 污染扩展侧缓存（前 3 类结果消息连 `source` 字段都不校验）。

### 界面入口现状与未移植项

- 已接入界面：按等级筛选导出、六格式批量导出、综合报告 MD、多目标聚合（选既往 JSON 结果）、教育/通用 Dork 包切换、仅高风险过滤、自定义 Dork 导入与备份导出、链接采集黑名单（设置页）、采集历史的逐份打开/删除/清空（设置页）、自定义密钥正则与敏感路径探测（设置页「扫描规则」）。这些能力的核心逻辑此前就已存在，缺的只是入口，现已全部接通并有断言覆盖。
- 页面职责：结果页只展示结果（外加导出与复制），不承担历史管理与结果切换；来源治理（允许域、参数、黑名单、采集历史）集中在设置页。
- 上游 CrazyEdusrc 的 `cleanDomain` / `extractSiteTarget`（从 `site:` 反解目标域）与三引擎翻页 URL 尚未移植。
- 主题只有暗色/亮色/极客三档，缺上游的 `system` 跟随系统档。

### 死字段与不匹配

- 已修复：`probes.routes.routeFullUrls` 由 `probe-routes` 产出并被综合报告消费；`collect-extras` 回填 `routes.routerBase` 并携带 `pageAnalysis` / `modifiedRoutes` / `logs`，`security-report` 的「检测到的基础路径」「已修改鉴权 Meta 的路由」「分析日志」三章不再恒空；`route-urls` 的 base 模式两个调用点都改为传入真实推断的 base。
- 仍存在：综合报告的「路由完整 URL」章节展示的是全量拼接结果，而实际探测只取前 40 条——这是刻意的上限，界面上已标明两个数字。`probes.routes.routeFullUrls` 已纳入存储降级上限（300 条），仅在写入配额失败时截断。

## 三、判定可靠性风险（容易误信的地方）

1. **"未受保护路由"只看 `meta` 的键名是否存在**，不看值（`requiresAuth: false` 也算已保护）、不看全局 `beforeEach`、不看懒加载子路由 → 极易虚报，也可能漏报。
2. **敏感路径探测的关键词过泛且不校验 Content-Type**：`.env` 只要含 `=`、`package.json` 只要含 `name`、`actuator` 只要含 `health` 即算命中；SPA 的历史回退路由对任意路径返回 200，会把伪造路径判成"存在"。
3. **路由可达性只看状态码与字节数**，`probe-routes` 明确丢弃响应体，200 不等于有内容。
4. **指纹匹配首个命中即返回**，且版本回退到"整条 URL 里抓版本号"；`/ATS/`、`/MT/`、`/mage/`、`XSRF-TOKEN→Laravel` 这类裸词正则会张冠李戴。
5. **响应头风险等级偏高**：HSTS 缺失记 high、CSP 缺失记 medium，非会话类 Cookie 缺 Secure 也一律 medium。
6. **弱信号即会触发 L3**：只要 `window` 里出现 vue/react 字样，`tech-stack` 就判定 SPA 并放行路由探测，进而注入接管脚本——即使该站点根本没有前端路由。
7. **自定义规则由导入者负责**：`userPatterns` 的正则在采集期直接执行，写了灾难性回溯的模式会拖慢甚至卡住本次采集（导入时只校验能否编译与长度，不评估复杂度）；`userProbes.keywords` 过泛（如只写 `id`、`=`）会把 SPA 的历史回退页判成命中。内置条目始终先于自定义条目生效且不会被顶掉，追加不会造成漏报，但会放大误报。

## 四、验证方式

ReconX 是构建型扩展，未引入测试框架。当前可复现的自动化校验有三类：

- **类型与构建**：`npm run typecheck`（`vue-tsc --noEmit`）、`npm run build`（额外产出三个 MAIN world IIFE 脚本并拷入 `dist/`）。
- **纯逻辑断言**（`esbuild` 打包核心模块后在 Node 直接跑，不依赖 Chrome）：双源主次判定、存储配额降级、资产测绘矩阵与侦察入口、导出链与 Dork 链（含以 Vue 响应式代理为入参的导出路径）。
- **background 行为回归**：用 mock 的 `chrome` 驱动真实消息处理器，覆盖实时回传串行写入、失败补排、空范围不注册、指令下发、统计字段形状、总开关三处联动。
- **端到端采集回归**：同一 mock 驱动真实 `collect()`，注入构造的页面 payload，验证链接归一后搜索引擎跳转被剔除、设置页黑名单命中被跳过、跳过条数与生效规则数如实写入 bundle。

以上开发期校验合计 169 条断言，不在扩展加载路径内，也不随 `npm run build` 执行。设置页与结果页的界面已对构建产物在浏览器中渲染核验（本地静态服务 + chrome API 桩），但这仍不等于扩展运行态。

## 五、需 Chrome 实测

以下只能靠加载 `dist/` 验证，目前**均为未验证状态**：

- `document_start` 下 `content.ts` 与常驻注册的 `all-in.js` 谁先执行，首帧状态上报是否丢失。
- 允许域为空、或 host 权限尚未授予时，manifest 里静态声明 `<all_urls>` 的 `content.ts` 到底会不会注入；若不注入，整条 `reconx*` 回传链路在授权前是否完全不通。
- 关闭「启用主动探测」总开关、或移除允许域后，该站点下一次加载确实不再被注入接管脚本。
- detector 注入锁卡死场景是否可复现。
- `crxjs` 产出的 WAR 路径与 `chrome.runtime.getURL('detector.js')` 是否解析一致。
- 主题切换在长表分页 + 子标签页下的视觉表现；三档主题与 Element Plus 配色联动。
- 授权弹窗、被动采集、主动探测、响应头捕获、导出下载等常规端到端流程。
- 新增界面项：设置页黑名单输入框（每行一条、`*.` 与 `/正则/` 写法）能否即时保存并在下一次采集生效；结果页概览「链接过滤」两个计数与规则数是否与实际一致；Dork 表类别/风险中文标签、行业全局查询表、自定义 Dork 导入与备份导出按钮。
- 设置页「扫描规则」分区：整批校验的拒绝提示是否可读、导出备份文件能否原样回灌、清除后内置规则是否照常命中。
- 采集历史：真实 Chrome 下连续采集多站后，设置页历史是否如实列出、逐份「打开」是否让结果页指向所选那份、删除与清空是否真正回收 `bundle:<id>` 键；配额吃紧时是否按预期丢最旧而不是让采集失败。
- 等级过滤下拉现在对六种格式、批量、综合报告、聚合导出统一生效（导出前一次性过滤），需确认界面表述与产出内容一致。
- `isEngineUrl` 的引擎域名表是否会误杀：目标本身是搜索引擎域、或站内链接指向引擎查询串时会被计入跳过。
